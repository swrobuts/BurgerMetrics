Git LFS: Zeigerdatei oder Daten

Git speichert jede Version einer Datei vollständig. Für die 15 CSV-Dateien des Datensatzes — zusammen 315 MB, allein obt_orders.csv 176 MB — bliebe jede Änderung für immer in der Historie. Git LFS (Large File Storage) legt deshalb im Repository nur eine kleine Zeigerdatei ab und die Daten in einem eigenen Speicher; die Regel dafür steht in .gitattributes: *.csv filter=lfs diff=lfs merge=lfs -text.

Die Zeigerdatei zu fact_orders.csv hat drei Zeilen und 133 Byte:

version https://git-lfs.github.com/spec/v1 oid sha256:deef61177fc57b004e792f5e72c400b5fb2658c665af107930253e8a25060e8d size 53346072

Die letzte Zeile nennt die Größe der eigentlichen Datei: 53.346.072 Byte, in ls -lh als 51M angezeigt. Wer das Repository ohne eingerichtetes Git LFS klont, bekommt für jede CSV-Datei genau diese drei Zeilen statt der Daten — und keine Fehlermeldung. Die Prüfung gehört deshalb zum Klonen dazu.

So sieht die Prüfung in beiden Fällen aus: mit Daten und mit Zeigerdatei.

Das Kontingent: 10 GiB je Monat

GitHub rechnet jeden Download aus dem LFS-Speicher auf das Kontingent des Repositorys an — auch bei Forks und Klonen: 10 GiB Bandbreite je Monat (Stand 09/2026). Ein Klon zieht 315 MB; das Kontingent reicht damit für rund 30 Klone im Monat. Für einen Kurs mit vielen Teilnehmenden gibt diese Grenze den Weg vor: Die Notebooks lesen große Tabellen aus der Datenbank, lade_csv() ist auf Dimensionen beschränkt, und wer den ganzen Bestand lokal will, klont einmal und arbeitet danach in DuckDB.

DuckDB: SQL auf CSV-Dateien, ohne Server

DuckDB ist eine Datenbank als Python-Paket: pip install duckdb, und SQL läuft direkt auf CSV- und Parquet-Dateien oder auf DataFrames — ohne Server, ohne Port, ohne Konto. Die Datenbank ist eine Datei, hier burger_metrics.duckdb, und sie gehört Ihnen: CREATE TABLE und CREATE VIEW, die die Rolle studi_daba in Lab 01 verweigert, sind hier erlaubt. Stand 09/2026: Version 1.5.5 vom 22.07.2026, daneben die LTS-Reihe 1.4, die die Notebooks der Fallstudie nutzen — für dieses Lab macht das keinen Unterschied.

Zwei Wege zur Datei: das Ladeskript des Repositorys für den ganzen Datensatz, oder wenige Zeilen Python für die Tabellen, die Sie gerade brauchen.

Weg 1: das Ladeskript

dataset/load_duckdb.py liegt im Repository. Es lädt alle 14 Tabellen in eine Datei und prüft jede Zeilenzahl gegen den Sollwert — ein unvollständiger Ladelauf fällt so sofort auf und nicht erst in der Übung.

Weg 2: read_csv

Für zwei Tabellen braucht es kein Skript. read_csv liest eine CSV-Datei mit erkannten Typen, CREATE TABLE … AS speichert das Ergebnis in der Datei, und die Abfrage darauf ist dieselbe wie gegen PostgreSQL — solange sie bei Standard-SQL bleibt.

Zum Maßstab: Für das Foliendeck der Vorlesung („Vom Datenmodell zur Entscheidung“) wurden die 13 CSV-Dateien des Kernbestands, 311,4 MB, mit DuckDB 1.5.5 geladen — Median aus sieben Läufen: Laden aus CSV 2,3 s, Datenbankdatei danach 54,5 MB, die Abfrage „Umsatz je Filiale und Jahr“ über zwei Verknüpfungen 3,9 ms. Die Datei ist kleiner als die CSV-Dateien, weil DuckDB spaltenweise und komprimiert speichert.

Hinweis. Bei den hier gezeigten Werkzeugen handelt es sich um eine Auswahl — sie ist weder als Empfehlung noch als Werbung zu verstehen. DuckDB steht hier, weil das Ladeskript und die Notebooks des Repositorys es verwenden. Wer die CSV-Dateien auf dem eigenen Rechner ohne SQL auswerten will, liest sie mit pandas (pd.read_csv) — derselben Bibliothek, mit der die Notebooks arbeiten (pandas 3.0, Stand 09/2026).

Exportformate: CSV, Parquet, Excel, .hyper

Ein Export ist eine Kopie und veraltet ab dem Moment, in dem er geschrieben ist. Wo er trotzdem nötig ist — Tableau Desktop Public Edition, eine Abgabe an ein anderes Team, ein Rechner ohne Datenbankverbindung —, entscheidet das Ziel über das Format.

CSV Text, in jedem Werkzeug und jedem Editor lesbar keine Typen: Datum und Dezimalzahl werden beim Einlesen geraten; die Kodierung muss der Leser kennen — die Dateien des Datensatzes sind UTF-8 mit BOM fact_orders.csv 51 MB; der Weg in Tableau Desktop Public Edition und in Excel

Stolpersteine

Vier Situationen, in denen der Weg zu den Daten scheitert oder still das Falsche liefert. Die Meldungen stehen hier wörtlich.

Zeigerdatei statt Daten. Ein Klon ohne Git LFS enthält 15 Zeigerdateien und meldet nichts. Erst das Ladeskript bricht ab, mit der Abhilfe in derselben Meldung:

FEHLER: Diese Dateien sind Git-LFS-Verweise, keine Daten:
Abhilfe: git lfs install && git lfs pull

Wer eine Zeigerdatei stattdessen selbst mit read_csv oder pd.read_csv liest, bekommt eine Tabelle mit einer Spalte und zwei Zeilen — und keine Fehlermeldung, bis die erste Abfrage eine Spalte wie branch_id sucht.

Colab liest Zeigerdateien. Die Roh-Adresse raw.githubusercontent.com/swrobuts/BurgerMetrics/main/dataset/dim_branch.csv liefert die Zeigerdatei, nicht die Daten. pd.read_csv liest sie ohne Beanstandung ein: eine Spalte namens version https://git-lfs.github.com/spec/v1, zwei Zeilen. Die nächste Zeile, die eine Spalte erwartet, scheitert mit KeyError: 'branch_id'. Die Notebooks nehmen deshalb media.githubusercontent.com/media/swrobuts/BurgerMetrics/main/dataset/… — diese Adresse liefert die Daten aus dem LFS-Speicher und zählt auf das Kontingent. Aus demselben Grund liegt notebooks/daten_extern/ ohne LFS im Repository.

Nachbildung der Oberfläche, Stand 09/2026 — Beschriftungen wie im Original.

  1. 1Die Roh-Adresse: pandas nimmt die erste Zeile der Zeigerdatei als Spaltenname und die beiden anderen als Werte. Kein Fehler, keine Filiale.

pandas 3 und DuckDB 1.4. pandas 3.0 speichert Text im neuen Standardtyp str. DuckDB 1.4 kennt diesen Typ beim Registrieren eines DataFrames noch nicht (Stand 09/2026):

NotImplementedException: Not implemented Error: Data type 'str' not recognized

Die Notebooks 00 und 01 setzen die Textspalten vor con.register() auf object — mit der Hilfsfunktion fuer_duckdb():

def fuer_duckdb(daten): # DuckDB 1.4 kennt pandas' neuen Standard-Stringtyp "str" (ab pandas 3) noch nicht spalten = {s: object for s in daten.columns if daten[s].dtype == "str"} return daten.astype(spalten) if spalten else daten con.register("dim_branch", fuer_duckdb(lade_csv("dim_branch")))

Zeitgrenze bei Vollabzügen. Die Rolle studi_daba darf je Abfrage zehn Minuten rechnen (Lab 01). Ein Vollabzug wie SELECT * FROM fact_order_items — 2.950.082 Zeilen — läuft über die Verbindung in ein Notebook gegen diese Grenze; bricht die Datenbank ab, lautet die Meldung:

ERROR: canceling statement due to statement timeout

Der Weg daran vorbei: in der Datenbank aggregieren — die Sichten v_* tun genau das — oder der ganze Bestand per DuckDB auf dem eigenen Klon.

Übungen

Fünf Übungen: zwei SQL-Aufgaben, deren Lösung wortgleich in DuckDB läuft, eine Reihenfolge vom Klon zur eigenen DuckDB-Datei, drei Fragen zu LFS, Parquet und Colab und eine Zuordnung von Ziel zu Weg.

Zusammenfassung

  • Drei Wege, ein Bestand: Am Connector rechnet die Datenbank und liefert über 38 Sichten fertige Kennzahlen; die CSV-Dateien aus Git LFS bringen 315 MB in 15 Dateien auf Ihren Rechner; DuckDB fragt sie dort mit SQL ab — in einer Datei, die Ihnen gehört.
  • Git LFS: git lfs install vor dem Klonen, dann ls -lh dataset/fact_orders.csv — 51M ist richtig, 133B ist eine Zeigerdatei, die mit version https://git-lfs.github.com/spec/v1 beginnt; Abhilfe git lfs pull. Das Kontingent von 10 GiB je Monat reicht für rund 30 Klone (Stand 09/2026).
  • DuckDB (1.5.5, LTS-Reihe 1.4; Stand 09/2026): load_duckdb.py --lokal lädt 14 Tabellen und prüft die Zeilenzahlen; read_csv und CREATE TABLE … AS holen einzelne Tabellen. Eine Abfrage in Standard-SQL läuft wortgleich in DuckDB und PostgreSQL.
  • Formate: CSV liest jedes Werkzeug, trägt aber keine Typen; Parquet hält Typen und komprimiert (fact_orders: 10,7 MB statt 51 MB); Excel endet bei 1.048.576 Zeilen je Blatt; .hyper ist Tableaus Extract.
  • Werkzeug und Weg: Power BI und Tableau Desktop über den Connector, Tableau Desktop Public Edition über CSV aus notebooks/export/, Colab über lade_sql(), lokal ohne Server über DuckDB.
  • Stolpersteine: Zeigerdatei statt Daten (raw.githubusercontent.com statt media.githubusercontent.com/media/…), der pandas-3-Typ str beim register() in DuckDB 1.4 (fuer_duckdb()), und statement_timeout bei Vollabzügen.
