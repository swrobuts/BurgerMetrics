Zugang und Datenbank

Dieses Lab verbindet Sie mit der Datenbank der Fallstudie BurgerMetrics: einem echten PostgreSQL, erreichbar über ein absichtlich öffentliches, nur lesendes Demo-Konto. Sie lernen die fünf Verbindungsangaben, die beiden Schemata wawi und burgermetrics, die Sichten als Vertrag für Kennzahlen — und was die Rolle nicht darf und woran Sie das in der Fehlermeldung erkennen.

Warum eine Rolle

Dashboard, Online-Shop und Notebooks der Fallstudie BurgerMetrics lesen alle dieselbe Datenbank. Für dieses und die folgenden Labs verbinden Sie sich direkt mit ihr — über ein eigens dafür angelegtes Konto: die Rolle studi_daba.

Das Kennwort dieses Kontos steht offen im Quelltext des Repositorys, in db/aufbau/0020_demo_rolle.sql. Das ist keine Nachlässigkeit: Das Konto ist eigens für Studierende angelegt, es liest ausschließlich, und der Bestand dahinter ist synthetisch — keine echten Personen, keine echten Bestellungen. Ein Kennwort zu verbergen ergibt nur Sinn, wenn es etwas schützt.

Was die Rolle nicht darf, darf über dieses Konto niemand: schreiben. Wer INSERT, UPDATE oder CREATE ausprobieren möchte, arbeitet mit DuckDB (Lab 02) — das läuft vollständig auf dem eigenen Rechner —, in der Datenbank dieser Seite (Abschnitt „Spielplatz“) oder richtet eine eigene Instanz ein. In diese Datenbank schreibt aus diesem Lab niemand.

Schemata und Suchpfad

Die Datenbank enthält zwei Schemata, die Sie in diesem Kurs wiederholt sehen: wawi, das operative Modell in dritter Normalform, in das Kasse und Online-Shop schreiben, und burgermetrics, das analytische Galaxy-Schema mit 38 materialisierten Sichten in der echten Datenbank. Im Miniaturbestand dieses Labs sind es sechs gewöhnliche Sichten, vier in burgermetrics und zwei in wawi; information_schema.views führt sie auf.

Beide Schemata liegen im Suchpfad der Rolle, in dieser Reihenfolge:

wawi, burgermetrics

Ein Name ohne vorangestelltes Schema wird in dieser Reihenfolge gesucht: Kennt wawi den Namen, gewinnt wawi — auch wenn burgermetrics denselben Namen ebenfalls vergeben hat. Genau das passiert bei v_rezension_produkt: Die Sicht existiert in beiden Schemata, mit unterschiedlichen Spalten. Ein Präfix ist deshalb immer dann nötig, wenn ein Name doppelt vorkommt.

Die ersten beiden Übungen weiter unten üben genau das: je Schema zählen, und das richtige Präfix wählen.

Sichten als Vertrag

Jede Kennzahl der Fallstudie ist genau einmal definiert — als Sicht. v_kennzahlen_jahr zum Beispiel definiert Bestellungen, Umsatz und durchschnittlichen Bestellwert je Jahr; für 2025 liefert sie in der echten Datenbank einen Umsatz von 2.994.771,13 €. Dashboard, Notebooks und die Dash-App der Fallstudie lesen alle dieselbe Sicht — wer die Definition ändert, ändert sie für jeden Leser auf einmal. Das ist der Sinn einer Semantikschicht: eine Kennzahl, ein Ort, keine abweichenden Nachrechnungen in jedem Werkzeug einzeln.

In der echten Datenbank sind diese Sichten materialisiert — vorab berechnet und gespeichert, damit ein Lesezugriff nicht bei jedem Aufruf 754.513 Bestellungen neu aggregiert. Im Miniaturbestand dieses Labs genügen dafür gewöhnliche Sichten auf 19 Bestellungen; das Ergebnis der Abfrage ist dasselbe, nur die Ausführung dahinter unterscheidet sich.

Rechte und Grenzen

Die Rolle studi_daba ist eng gefasst: lesen ja, in klaren Zeit- und Sitzungsgrenzen, schreiben nie.

Erlaubt
  • SELECT auf alle Tabellen, Sichten und materialisierten Sichten in wawi und burgermetrics
  • EXECUTE auf burgermetrics.kurzname(text) — kürzt Produktnamen für Diagramme
Begrenzt
  • eine Abfrage läuft höchstens 10 Minuten (statement_timeout)
  • eine offene Transaktion läuft höchstens 5 Minuten leer (idle_in_transaction_session_timeout)
  • höchstens 20 gleichzeitige Sitzungen
Verboten
  • INSERT, UPDATE, DELETE, CREATE — in einer Standardsitzung zuerst durch die nur lesende Voreinstellung verhindert (default_transaction_read_only = on, mit SET TRANSACTION READ WRITE abschaltbar); wer sie abschaltet, scheitert an den fehlenden Rechten (ACLs) auf jede Tabelle, jedes Schema und jede Funktion.
  • EXECUTE auf wawi.bestellung_anlegen() und wawi.rezension_anlegen()
  • eigene Rechte im Schema public — die Rolle hat dort weder USAGE noch CREATE; SELECT * FROM public.xyz endet deshalb mit permission denied for schema public, nicht mit relation … does not exist

Stolpersteine

Vier Ursachen erzeugen die Fehlermeldungen, denen Sie mit dieser Rolle begegnen. Alle Meldungen stehen hier wörtlich — so erscheinen sie auch bei Ihnen.

Falsches oder fehlendes Schema. Ein Name ohne Präfix trifft im Suchpfad zunächst wawi (Abschnitt „Schemata und Suchpfad“) — das ist kein Fehler, nur eine andere Sicht als vielleicht gemeint. Ein Fehler wird daraus erst, wenn ausdrücklich ein Schema genannt wird, auf das die Rolle keine USAGE-Berechtigung hat, etwa public:

ERROR: permission denied for schema public

Ein unbekannter Name ganz ohne Präfix liefert weiterhin relation "xyz" does not exist — der Suchpfad enthält public nicht.

Nur lesende Transaktion. Jede verändernde Anweisung scheitert an derselben Voreinstellung, ob sie eine Zeile einfügt oder eine Tabelle anlegt:

ERROR: cannot execute INSERT in a read-only transaction
ERROR: cannot execute CREATE TABLE in a read-only transaction

Fehlendes Ausführungsrecht. Die Rolle darf keine der beiden schreibenden Funktionen aufrufen:

ERROR: permission denied for function bestellung_anlegen

Zeit- oder Sitzungsgrenze. Läuft eine Abfrage länger als zehn Minuten, bricht PostgreSQL sie ab:

ERROR: canceling statement due to statement timeout

und bei mehr als zwanzig gleichzeitigen Sitzungen der Rolle verweigert die Datenbank eine weitere Anmeldung von vornherein:

FATAL: too many connections for role "studi_daba"

Die Zuordnungsübung weiter unten stellt sechs Meldungen diesen vier Ursachen gegenüber.

Spielplatz

Unten läuft ein vollständiges PostgreSQL im Browser (PGlite, WebAssembly) mit dem Miniaturbestand dieser Fallstudie: 19 Bestellungen, 55 Positionen und 12 Rezensionen in denselben beiden Schemata und demselben Suchpfad wie die echte Datenbank. Es ist kein Simulator — dieselben Datentypen, dieselben Fehlermeldungen. Was Sie hier schreiben, wirkt nur in diesem Browserfenster.

Probieren Sie aus, was in den Abschnitten oben vorkam — Suchpfad, Präfix, die Sichten. Der Knopf Datenbank zurücksetzen stellt den Ausgangsbestand wieder her.

Übungen

Sechs Übungen: drei SQL-Aufgaben gegen die Datenbank oben, eine Verständnisfrage zur Rolle, eine Zuordnung von Fehlermeldung zu Ursache und eine Checkliste für die echte Verbindung mit einem Werkzeug Ihrer Wahl.

Zusammenfassung

  • Das Demo-Konto studi_daba / thws ist absichtlich öffentlich: nur lesend, auf einen synthetischen Bestand — das Kennwort im Quelltext ist deshalb kein Versehen.
  • Fünf Angaben oder die gleichwertige URI verbinden gleichermaßen mit psql, DBeaver Community 26.2.0 oder DataGrip 2026.2 (Stand 09/2026); welches Werkzeug Sie wählen, ändert nichts an der Datenbank dahinter.
  • Zwei Schemata, ein Suchpfad: wawi (operativ) vor burgermetrics (analytisch) — bei doppelten Namen wie v_rezension_produkt entscheidet die Reihenfolge, und ein Präfix macht die Wahl ausdrücklich.
  • Sichten sind der Vertrag für Kennzahlen: jede genau einmal definiert, in der echten Datenbank materialisiert, von Dashboard, Notebooks und Dash-App gemeinsam gelesen.
  • Die Rolle liest beide Schemata vollständig und schreibt nichts — begrenzt durch Zeit- und Sitzungsgrenzen, nicht durch fehlende Sichtbarkeit.
  • Vier Ursachen erklären jede Fehlermeldung dieser Rolle: falsches Präfix, nur lesende Transaktion, fehlendes Ausführungsrecht, Zeit- oder Sitzungsgrenze.
  • Die Verbindung, die Sie hier herstellen, brauchen Sie in Lab 02, Lab 04, Lab 05 und Lab 06 wieder.
