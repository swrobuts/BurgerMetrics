## 1 Ziel

Studierende des Moduls *Datenbasierte Fallstudien* sollen mit dem BurgerMetrics-Bestand
eigenständig analysieren können: sich an der Datenbank anmelden, Daten für Power BI, Tableau
und Python beschaffen, ein analytisches Datenmodell schrittweise aufbauen, Data-Mining-Verfahren
anwenden und externe Daten anbinden. Dafür entstehen vier Dinge:

1. ein Foliendeck `BurgerMetrics_3_Analyse.pptx` als dritter Teil der bestehenden Reihe,
2. neun Jupyter-Notebooks und eine Dash-App im BM-Repo,
3. eine Erweiterung des Bestands um **Rezensionen** (Datenbank, Generator, Shop-Feature),
4. eine interaktive Lernumgebung **BM-Lab** als eigenes Repo auf GitHub Pages.

**Produktionsbereite Übergabe.** Robert führt vor oder in einer Lehrveranstaltung keine
Skripte aus und arbeitet dort oft nicht am eigenen Rechner. Deshalb gilt für jede Phase: Was
gebaut wird, wird von der Sitzung selbst in Betrieb genommen — Aufbauskripte auf der
Instanz eingespielt (über den MCP-Server `burgermetrics-db`, `ausfuehren()`), CSV geladen,
Sichten materialisiert, Seiten veröffentlicht, Notebooks ausgeführt, Verweise gesetzt. Eine
Phase ist erst abgeschlossen, wenn der Stand ohne weiteren Handgriff nutzbar ist.

Zielgruppe: Bachelor Business Analytics ohne tiefe Programmiererfahrung. Alles Material ist
sachlich, nur deutsch, englische Fachbegriffe bleiben englisch, echte Umlaute, Code für
Anfänger (kurze Funktionen, deutsche Namen, ein Kommentar je Funktion, keine Tricks).

## 3 Rezensionen — Datenbank

Neue Datei `db/aufbau/0021_rezensionen.sql`, idempotent, Kopfkommentar wie die anderen
(Zweck, Voraussetzung, Objekte, Rücknahme).

### 3.1 Operativ: `wawi.rezension`

```sql
CREATE TABLE IF NOT EXISTS wawi.rezension (
  rezension_id  bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  artikel_id    bigint NOT NULL REFERENCES wawi.artikel(artikel_id),
  kunde_id      bigint REFERENCES wawi.kunde(kunde_id),
  bestellung_id bigint REFERENCES wawi.kundenbestellung(bestellung_id) ON DELETE SET NULL,
  filiale_id    bigint REFERENCES wawi.filiale(filiale_id),
  sterne        smallint NOT NULL CHECK (sterne BETWEEN 1 AND 5),
  inhalt        text NOT NULL CHECK (char_length(inhalt) BETWEEN 5 AND 500),
  erstellt_am   timestamptz NOT NULL DEFAULT now(),
  quelle        text NOT NULL CHECK (quelle IN ('simulation', 'shop')),
  sitzung       text
);
```

Indizes auf `artikel_id`, `kunde_id`, `erstellt_am`. Row Level Security mit Policy
`lesen_alle` wie alle `wawi`-Tabellen. Nach dem Bestandsimport wird die Identity auf
`max(rezension_id) + 1` gesetzt.

**Schreibfunktion** `wawi.rezension_anlegen(artikel_id bigint, sterne integer, inhalt text,
filiale_id bigint DEFAULT NULL, sitzung text DEFAULT NULL) RETURNS jsonb` — nach dem Muster von
`bestellung_anlegen()`: `SECURITY DEFINER`, `SET search_path = wawi, pg_temp`,
`#variable_conflict use_variable`. Prüfungen: Artikel bekannt, Sterne 1–5, Text nach `btrim`
5–500 Zeichen, Filiale bekannt falls angegeben. Bremse: höchstens 20 Rezensionen je Sitzung in
zehn Minuten (`ERRCODE 53400`). `quelle` ist fest `'shop'`, `kunde_id` bleibt leer (der Shop hat
kein Kundenkonto). Rückgabe `{"rezension_id", "artikel", "sterne", "erstellt_am"}`. Rechte:
`REVOKE ALL FROM PUBLIC`, `GRANT EXECUTE TO anon, authenticated`, ausdrücklich `REVOKE` für
`studi_daba`.

**Sichten:**

* `wawi.v_rezension_produkt` — je Artikel: `artikel_id`, `name`, `anzahl`, `sterne_mittel`
  (auf eine Nachkommastelle), `letzte` (Datum). Über alle Quellen.
* `wawi.v_kundenstimmen` — die drei jüngsten Rezensionen je Artikel mit `quelle = 'simulation'`
  (Sterne, Text, Datum) für die Anzeige im Shop. **Nur** Simulationstexte, nie Besuchertexte.
* `wawi.v_rezension_letzte` — die 50 jüngsten Shop-Rezensionen mit `im_warehouse` (wie
  `v_bestellung_letzte`).

**Rücksetzen:** `wawi.uebungsrezensionen_loeschen()` löscht `quelle = 'shop'` in beiden
Schemata und gibt die Zahlen zurück.

### 3.2 Analytisch: `burgermetrics.fact_reviews`

```sql
CREATE TABLE IF NOT EXISTS burgermetrics.fact_reviews (
  review_id   bigint PRIMARY KEY,
  date        date NOT NULL REFERENCES burgermetrics.dim_date(date),
  time        time,
  customer_id bigint REFERENCES burgermetrics.dim_customer(customer_id),
  product_id  bigint NOT NULL REFERENCES burgermetrics.dim_product(product_id),
  branch_id   bigint REFERENCES burgermetrics.dim_branch(branch_id),
  order_id    bigint REFERENCES burgermetrics.fact_orders(order_id),
  stars       smallint NOT NULL CHECK (stars BETWEEN 1 AND 5),
  review_text text NOT NULL,
  source      text NOT NULL CHECK (source IN ('simulation', 'shop'))
);
```

Indizes auf `date`, `product_id`, `customer_id`. Row Level Security mit Policy `lesen_alle`
wie alle Tabellen in `burgermetrics` (0004). Grain: eine Rezension. Kennzahl in der
Semantikschicht: `burgermetrics.v_rezension_produkt` (materialisiert wie die anderen `v_*`):
je Produkt `product_name`, `category`, `anzahl`, `sterne_mittel`, `anteil_positiv` (4–5
Sterne), `anteil_negativ` (1–2 Sterne). `materialisieren.py` nimmt die Sicht automatisch mit.

**ETL** (Erweiterung von `0019`, in `0021`): Sicht `wawi.stg_fact_reviews` (nur
`quelle = 'shop'`, Spaltennamen ins Auswertungsvokabular). `burgermetrics.uebernahme_aus_wawi()`
wird per `DROP FUNCTION` + `CREATE` um `neue_rezensionen integer` in der Rückgabe erweitert; die
Tage-Ergänzung in `dim_date` berücksichtigt auch Rezensionsdaten. `wawi.etl_probe()` bekommt
eine Zeile `rezension`.

### 3.3 Ladeweg

CSV bleibt Quelle der Wahrheit: `dataset/fact_reviews.csv` (LFS) → `db/lade_csv.py`
(`REIHENFOLGE` um `fact_reviews` ergänzt, nach `fact_order_items`) → `burgermetrics.fact_reviews`
→ `0021` kopiert die Zeilen mit `source = 'simulation'` einmalig nach `wawi.rezension`
(Muster `0017_wawi_bestand.sql`), gleiche IDs; `date` + `time` werden zu `erstellt_am` in
`Europe/Berlin`, `product_id`/`branch_id`/`customer_id` bleiben Zahlen, weil die Stammdaten in
beiden Schemata dieselben Schlüssel tragen (0016 — in der Umsetzung gegen `wawi_zu_analytisch.sql`
prüfen). Danach läuft der ETL nur für Shop-Rezensionen.

Mini-Skripte: `dataset/burgermetrics_mini.sql` und `dataset/wawi_mini.sql` bekommen je zwölf
Rezensionen zu vorhandenen Belegen, `dataset/wawi_zu_analytisch.sql` die Abbildung
`rezension → fact_reviews` — der Nachweis lautet dann „neun von neun zeilengleich".

### 3.4 Rechte und Proben

`0021` läuft **als `postgres`** (über den MCP-Server oder `psql` mit dem Betreiberkonto), nicht als
`supabase_admin`: Die Default-Privileges aus 0020 und 0018 gelten nur für Objekte, die `postgres`
anlegt. Unabhängig davon setzt das Skript die Rechte ausdrücklich — `GRANT SELECT` auf
`wawi.rezension`, `burgermetrics.fact_reviews` und die neuen Sichten an `studi_daba`, `anon`,
`authenticated`; `ENABLE ROW LEVEL SECURITY` plus Policy `lesen_alle` auf beiden Tabellen —, damit
kein Leserecht an der Reihenfolge der Ausführung hängt. Stand 12.09.2026, live geprüft: `studi_daba`
liest alle 71 Objekte beider Schemata, schreibt keines, darf `bestellung_anlegen()` nicht ausführen
und sieht das Schema `velocity` nicht. Das Skript endet mit einem `DO`-Block, der prüft: `studi_daba` liest `wawi.rezension` und
`burgermetrics.fact_reviews`, schreibt keines, darf `rezension_anlegen()` nicht ausführen;
`anon` darf sie ausführen; Zeilenzahl `fact_reviews` = Zeilenzahl `rezension` mit
`quelle = 'simulation'` = 10.000.

## 4 Rezensionen — Generator und Glättung

### 4.1 Generator `dataset/generate_reviews.py`

Deterministisch (`random.seed(2026)`, `numpy` mit Generator und festem Seed), liest die
CSV-Dateien per DuckDB. Läuft mit `python3 dataset/generate_reviews.py` und schreibt den
Rohstand `dataset/fact_reviews_roh.csv` (LFS, versioniert); zwei Läufe liefern byte-identische
Dateien (Prüfung per Hash). Der geglättete Bestand `dataset/fact_reviews.csv` entsteht in 4.2.

**Auswahl.** 10.000 Bestellpositionen aus `fact_order_items` × `fact_orders` (alle Bestellungen
tragen `customer_id`), höchstens eine Rezension je Bestellung, keine Produkte der Kategorie
`Extra` (Saucen). Gewichte: Jahr linear steigend (2017 = 1 bis 2026 = 4),
Kanal App Order ×3, Kiosk ×1,5, sonst ×1; Kunden mit `has_app` ×2.

**Sterne.** Latente Größe `z = 1,2 · (satisfaction_score − 3,8) − 0,03 · (order_duration_min − Median)
+ produktniveau + ε`, `ε ~ N(0; 0,6)`; `produktniveau` je Produkt fest aus einer Tabelle im
Skript (z. B. Truffle Deluxe +0,4, Fish Burger −0,3, Water 0). Schwellen so gesetzt, dass etwa
5★ 38 %, 4★ 27 %, 3★ 13 %, 2★ 9 %, 1★ 13 % entstehen (Toleranz ±3 Punkte, wird geprüft).
Damit hängen Sterne messbar an Zufriedenheit und Bestelldauer der Bestellung — das ist die
Struktur, die das Sentiment-Notebook nachweisen soll.

**Datum und Zeit.** `date` = Bestelldatum + 0–3 Tage, begrenzt auf `2026-03-31` (Ende von
`dim_date`); `time` aus einer Tagesverteilung mit Abendspitze.

**Text.** Bausteine in `dataset/rezension_bausteine.json`, deutsch, je Sternestufe:
Einstieg (≥ 25 je Stufe), Produktsatz je Kategorie Burger/Side/Drink/Dessert/Breakfast (≥ 20 je
Kategorie und Polarität, mit Platzhalter `{produkt}`), Kontextsatz (Wartezeit ↔
`order_duration_min` in Klassen, Kanal ↔ `order_channel`, Filiale ↔ `branch_name` mit
Wahrscheinlichkeit 0,3, Preis ↔ Aktion/Rabatt), Schluss (Empfehlung ↔ Sterne). Ein bis vier
Sätze, 10–60 Wörter. Rund 15 % der Texte umgangssprachlich: Kleinschreibung, „ae/oe/ue" statt
Umlaute, mehrfache Satzzeichen — **kein Emoji**. Keine echten Personen, keine Beleidigungen,
keine Markennamen außer den Produktnamen des Bestands.

**Spalten der CSV:** `review_id, date, time, customer_id, product_id, branch_id, order_id,
stars, review_text, source` (`source` = `simulation`). Texte in Anführungszeichen, UTF-8,
Zeilenumbrüche im Text nicht erlaubt.

### 4.2 Glättung in Claude Code

Nach dem Generatorlauf werden die Texte sprachlich geglättet — in der Sitzung, nicht über die
API. Ablauf:

1. `dataset/glaettung/lose_schreiben.py` teilt `fact_reviews_roh.csv` in 100 Lose à 100 Texte
   (`lose/los_001.csv` … mit `review_id, stars, review_text`).
2. Je Los ein Subagent mit festem Prompt: Text natürlicher formulieren; Bedeutung, Sterne,
   Produkt- und Filialnamen, Polarität und Stilebene (umgangssprachlich bleibt
   umgangssprachlich) erhalten; Länge ±30 %; keine neuen Fakten, keine Emojis, kein Englisch;
   Ausgabe als CSV mit `review_id, review_text`. Ergebnis nach `lose/geglaettet_001.csv`.
3. `dataset/glaettung/zusammenfuehren.py` prüft Vollständigkeit (jede `review_id` genau
   einmal), Längen (5–500 Zeichen, ±30 % zum Original), keine Zeilenumbrüche, und schreibt
   `dataset/fact_reviews.csv`. Lose werden nicht versioniert (gitignore); Rohstand und
   geglätteter Bestand liegen beide im Repo, geladen wird nur der geglättete.
4. Stichprobe: 50 zufällige Texte werden gegen ihre Sterne gelesen; Abweichungen werden
   korrigiert oder das Los wiederholt.

Abbruchkriterium: Reicht die Zeit nicht für 100 Lose, werden die Lose in zufälliger
Reihenfolge geglättet und der Stand im README genannt (z. B. „6.000 von 10.000 geglättet").

## 6 Notebooks (`notebooks/`)

### 6.1 Konventionen

* Jedes Notebook beginnt mit denselben Abschnitten: **Fragestellung · Daten · Vorgehen ·
  Ergebnis · Was offen bleibt.** Sachlicher Ton, ganze Sätze, keine Bilder oder Pointen — auch in
  `print()`-Ausgaben.
* Eine **Verbindungszelle** je Notebook, keine versteckten Module:

  ```python
  import pandas as pd
  from sqlalchemy import create_engine

  VERBINDUNG = "postgresql+psycopg2://studi_daba:thws@supabase.butscher.cloud:5433/postgres"
  engine = create_engine(VERBINDUNG)

  def lade_sql(sql):
      # Führt eine Abfrage aus und gibt das Ergebnis als DataFrame zurück
      return pd.read_sql(sql, engine)

  def lade_csv(name):
      # Liest eine CSV-Datei des Datensatzes direkt aus GitHub (Git LFS)
      url = f"https://media.githubusercontent.com/media/swrobuts/BurgerMetrics/main/dataset/{name}.csv"
      return pd.read_csv(url)
  ```

  Große Tabellen (`fact_orders`, `fact_order_items`, `obt_orders`) werden aus der Datenbank
  gelesen, `lade_csv` nur für Dimensionen und zur Demonstration — das schont das LFS-Kontingent.
* Code für Anfänger: kurze Funktionen, deutsche Bezeichner, ein Kommentar je Funktion, keine
  verketteten Einzeiler, Ergebnisse als DataFrame anzeigen statt drucken.
* Diagramme mit matplotlib (Standardfarben, beschriftete Achsen, Nullpunkt bei Länge und Fläche),
  keine Wortwolken.
* Am Kopf ein „In Colab öffnen"-Link und eine `pip`-Zelle (`sqlalchemy psycopg2-binary duckdb
  scikit-learn mlxtend statsmodels holidays dash`); `notebooks/requirements.txt` daneben.
* Ausgeführt eingecheckt (GitHub rendert die Ergebnisse); `notebooks/pruefe_notebooks.sh`
  führt alle per `jupyter nbconvert --execute --to notebook --inplace` aus und ist die Abnahme.

## 13 Risiken und offene Punkte

* **LFS-Kontingent.** GitHub gibt 1 GB Bandbreite je Monat für LFS; ein Kurs, der die großen
  CSV-Dateien aus Colab lädt, überschreitet das. Deshalb lesen die Notebooks große Tabellen aus
  der Datenbank; `lade_csv` steht nur für Dimensionen. Auf den Folien wird das benannt.
* **Erreichbarkeit von Port 5433 aus Colab** ist plausibel (der Port ist öffentlich), aber
  in der Umsetzung zu Beginn von Phase 4 einmal zu prüfen.
* **OpenLigaDB** deckt die Regionalliga Bayern möglicherweise nicht ab; dann eine kleine, von
  Hand gepflegte CSV der Heimspieltage mit Quellenangabe.
* **Glättungsvolumen.** 10.000 Texte in 100 Losen sind viel Ausgabe; das Abbruchkriterium in
  4.2 hält den Bestand konsistent, auch wenn nicht alle Lose geglättet werden.
* **Synthetischer Bestand.** Effekte externer Daten sind nicht real; jedes Notebook, das externe
  Daten nutzt, sagt das im Abschnitt „Was offen bleibt".
* **Tableau und Nur-Lese-Transaktionen.** `studi_daba` hat `default_transaction_read_only = on`;
  Tableau legt für manche Filter und Extrakte temporäre Tabellen an, was dann scheitert. In der Regel
  weicht Tableau selbst aus — in Phase 6 mit dem Demo-Konto durchspielen und im Lab 05 als
  Stolperstein mit der wörtlichen Meldung aufnehmen, falls sie auftritt.
* **Öffentlicher Schreibweg.** Wie bei Bestellungen: Längen- und Ratenbegrenzung, keine
  Anzeige von Besuchertexten, Rücksetzfunktion. Ein Missbrauch verändert keine Kennzahl des
  kuratierten Bestands, weil der ETL bewusst aufgerufen wird.
